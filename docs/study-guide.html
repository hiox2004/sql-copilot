Basics

The big picture

A user types a question in English. The system must return correct, safe SQL and its result. A small language model alone would fail, so the work is split into four stages, each doing one job.

Analogy: a restaurant kitchen. Retrieve is the prep cook fetching only the ingredients needed. Generate is the chef. Verify is tasting before it leaves. Guard is the health inspector who makes sure nothing dangerous reaches the customer.
The key design rule: knowledge (retrieval) is kept separate from behavior (the model). Facts change often, so they are looked up. Skills (format, dialect style, fixing errors) change rarely, so they are trained.
Basics

SQL and Postgres in 10 minutes

A relational database stores data in tables (rows and columns). Tables link through keys. SQL is the language for asking questions.

Keys

PK and FK

Primary key uniquely names a row. Foreign key points at another table's primary key. FKs are the "roads" our graph walk follows.

Query

The core clauses

SELECT columns, FROM table, JOIN to link tables, WHERE to filter rows, GROUP BY + aggregates (SUM, COUNT) to summarize, ORDER BY, LIMIT.

Postgres

A dialect

SQL varies by database. Postgres uses NOW() - INTERVAL '30 days', ::int casts, ILIKE. MySQL spells these differently, which is why we isolate dialects.

SELECT o.name, SUM(s.mrr_cents) / 100.0 AS lost_usd
FROM subscriptions s
JOIN organizations o ON o.id = s.org_id
WHERE s.status = 'canceled'
GROUP BY o.name
ORDER BY lost_usd DESC
LIMIT 10;
Gotcha: valid is not correct. The query above runs fine even if "canceled" should have included "past_due". The database cannot know your business rules, which is why the data dictionary exists.
Basics

How a language model works (just enough)

Tokens

Text becomes pieces

The model reads and writes tokens (word fragments). Roughly 1 token ≈ 3-4 characters. Everything has a token budget: the context window.

Next token

It predicts, not knows

It repeatedly picks the likely next token. That is why it can write confident SQL for a column that does not exist.

Parameters

Size = 1.5B, 3B, 7B

"B" = billions of learned numbers (weights). Bigger is usually smarter but needs more memory. We pick small models so they run on modest hardware.

Prompt

Input = instructions + context

Our prompt holds the question, retrieved table definitions, rules, and the required JSON format. Same builder in training and production.

Why we cannot paste the whole schema. 80 tables × many columns = thousands of tokens of noise. Small models drown in it. Also "lost in the middle": models use the start and end of a long prompt better than the middle, so the most relevant tables go first.

What Text-to-SQL is and why it is hard

Problem 1

Schema explosion

Too many tables/columns. Fix: retrieval prunes to a handful.

Problem 2

Business meaning

"Churn", "big account" are company rules, not columns. Fix: data dictionary.

Problem 3

Dialect + mistakes

Wrong syntax, hallucinated columns. Fix: fine-tune + verify loop.

Problem 4

Ambiguity

"Top accounts" by what? Fix: ask the user (clarify step) and show assumptions.

Realistic expectations. Published top systems scored about 55% on BIRD and about 21% on Spider 2.0 at release (per the research library; verify before citing). Real databases are hard, so measure honestly and compare against a baseline.

Docker: your database in a box

Docker runs programs in isolated containers built from images. We use it so Postgres works the same on every machine and can be wiped and rebuilt in seconds.

  • Image = recipe/snapshot (postgres:16). Container = a running copy. Delete the container, the image remains.
  • Volume = storage that survives container deletion. Our pgdata volume keeps data. down -v deletes it.
  • Port mapping 127.0.0.1:5432:5432 = reachable only from your own machine, not the network.
  • Compose = one YAML file (infra/docker-compose.yml) that describes the services. Later we may add the API there (the model server runs natively on Windows, not in Docker).
  • Init scripts in infra/postgres/init/ run once on an empty volume to create the read-only role.
  • .env holds passwords; docker compose --env-file .env injects them. It is gitignored.
# start (from repo root)
docker compose -f infra/docker-compose.yml --env-file .env up -d
docker ps                                   # is it running / healthy?
docker exec -it t2sql-postgres psql -U admin -d saas
docker compose -f infra/docker-compose.yml logs postgres
docker compose -f infra/docker-compose.yml down        # stop, keep data
docker compose -f infra/docker-compose.yml down -v     # stop, DELETE data
Gotcha: init scripts only run when the volume is empty. If you change 01_roles.sh later, run down -v then up -d to re-run it. Also, Docker Desktop must be running before any docker command works.

Schema design: a 36-table SaaS database

The copilot is only as good as the database it reads. We built a realistic fake SaaS company in data/schema/. Docker loads the files in name order on first start: 01_schema and 02_schema_extra (tables), 03_seed_core and 04_seed_extra (fake rows), 99_checks (consistency checks that abort the build if the data is inconsistent). The diagram below shows the core 8 tables; 28 more surround them.

Money in cents

Integers, not floats

Binary FLOAT cannot store 0.1 exactly (0.1+0.2 ≠ 0.3). Postgres NUMERIC/DECIMAL is exact, but integer cents is a common convention: fast, exact, safe across languages. Cost: the model must remember to divide by 100.0, so the dictionary says so.

CHECK constraints

Impossible states blocked

e.g. canceled_at is set exactly when status = 'canceled'. Constraints keep the fake data honest, which keeps training data clean.

Bridge table

order_items

Orders and products are many-to-many, so revenue-by-product must join through order_items. Forgetting a bridge table is a classic text-to-SQL error (the FK graph walk fixes it).

Two nullable FKs

payments

A payment belongs to an order or an invoice. "Total revenue" is therefore ambiguous: it could mean order payments, invoice payments, or both. The dictionary must define it.

Seeded randomness

setseed(0.42)

Same fake data on every rebuild, so eval answers never drift.

COMMENT ON

Built-in documentation

Table/column comments live in the database itself and are raw material for the data dictionary.

PII. users.email and users.full_name are personal data. They never go into the dictionary or index, and the parser blocks them.

Consistency checks: tests for data

99_checks.sql holds 35 queries. Each counts violations of a rule (an invariant: something that must always be true) and must return 0. Examples: no invoice after cancellation; an order's total equals the sum of its items; a user's last_login_at equals their latest successful login; feature usage never happens after a subscription ends. Four more rules guard the variety of the data (at least 8 recent churns, 15 enterprise subscriptions, and so on). Run them any time:

docker exec t2sql-postgres psql -U admin -d saas \
  -v ref_now="'2026-11-05 12:00:00+00'" -f /schema/99_checks.sql
We proved the checks can fail. All 35 passed on the first run, which is suspicious: a check that cannot fail is worthless. So we corrupted the data inside a transaction (future cancellation, invoice after cancel, wrong order total, fake login, org with no users, usage after cancel) and ran the checks. They named every corruption, and the rollback left the real data untouched. Always test your tests.
Known limits. The data is still synthetic and simple: revenue and amounts are uniform-ish, there is little seasonality, and "downgraded" has only 3 cases (the minimum the check allows). Windows tip: Git Bash rewrites paths like /schema/x.sql; prefix commands with MSYS_NO_PATHCONV=1 when passing container paths.
Lesson: auditing data with SQL before building on it is a habit worth keeping. Every v1 bug would have silently corrupted golden answers.

A Python project, properly set up

Before the first line of real code, three things must exist: an isolated environment, a package definition, and a way to run tests. Skipping them is how "works on my machine" bugs are born.

Virtual environment

.venv

A private folder of Python packages for this project only. Installing here cannot break other projects or your system Python. Delete it and recreate it any time.

pyproject.toml

The project's ID card

Name, version, minimum Python, dependencies and tool settings in one file. pip install -e ".[dev]" reads it. The [dev] part adds optional extras (pytest, ruff).

Editable install

-e

Instead of copying the code into the venv, pip links to your folder. Edit a file and the change is live; no reinstall. Without it, import t2sql would fail or load a stale copy.

src layout

src/t2sql/

Code lives under src/, so tests can only import it after it is properly installed. That catches packaging mistakes early instead of in production.

Runtime vs dev

Runtime dependencies (pydantic, pyyaml, psycopg, python-dotenv) ship with the app. Dev tools do not. Heavy ML libraries stay out of both: they belong with the training notebooks.

pytest + markers

Fast unit tests need nothing. Integration tests (marker integration) need the database and skip themselves cleanly when it is down, so pytest never fails just because Docker is off.

ruff

One fast tool for lint and import sorting. Rules enabled: pycodestyle (E), pyflakes (F), isort (I), bugbear (B), pyupgrade (UP).

What the first tests protect

  • The package imports and every sub-package exists (layout is wired up).
  • The database has 36 tables when reached through the read-only role.
  • Safety layer 1 as a test: an INSERT through the read-only role must fail with a read-only-transaction error. If someone ever loosens the role, this test turns red.
  • No order is dated after the pinned "today" (a regression guard for the pinned-date decision).
Lesson from a warning. The first install printed a deprecation warning: declaring the license as a table (license = {text = "MIT"}) is going away. The fix was license = "MIT" plus setuptools>=77. Read warnings when they appear; they are cheapest to fix on day one.

"Saved" can mean three different things. We have all three.

1 Rebuildable

Seed files are the truth

The data/schema/*.sql files in git recreate the database exactly (pinned date, seeded randomness). Snapshots are a convenience; the recipe is the source of truth.

pg_dump writes a plain .sql file (1.8 MB for ours) to data/snapshots/. You can open it in an editor, copy it, or load it into any Postgres. It is gitignored because it is reproducible.

Loads the snapshot into a separate database, saas_scratch, so you can run INSERT/UPDATE/DELETE and broken queries freely. Re-running resets it. It refuses to overwrite the real saas.

Browser

Optional GUI at http://localhost:5050 (compose profile tools, no login in desktop mode). Browse tables, view rows, run queries, see the ER structure. The first connection asks for the admin password from your .env.

Working

Retrieval (RAG): look up, then write

Retrieval-augmented generation = fetch relevant facts first, then let the model write using them. We retrieve schema and rules, never row data.

Embeddings

Meaning as numbers

An embedding model turns text into a vector (e.g. 384 numbers). Similar meanings land near each other, so "client" ≈ "organization". Closeness is measured by cosine similarity.

BM25

Exact word matching

A classic keyword score that rewards rare matching words like mrr_cents. Embeddings can blur such names; BM25 nails them.

Fusion

RRF merges rankings

Reciprocal rank fusion: score = Σ 1/(k + rank) over each list (k≈60). Items ranked well by both float to the top, no score tuning needed.

Reranker

A second, sharper look

A slower model re-scores only the top ~20 candidates against the question. Cheap because the list is short.

FK graph walk: never lose a bridge table

Tables are nodes, foreign keys are edges. If search finds orders and payments, compute the shortest path between them and add the tables on it (e.g. order_items). Library: networkx.

def rrf(rankings, k=60):
    scores = {}
    for ranking in rankings:                 # e.g. [dense_list, bm25_list]
        for rank, doc in enumerate(ranking, start=1):
            scores[doc] = scores.get(doc, 0) + 1 / (k + rank)
    return sorted(scores, key=scores.get, reverse=True)
Gotcha: retrieval quality caps everything after it. If the right table is not retrieved, no model can fix it. Measure recall@k (did the needed tables appear in the top k?) separately from SQL accuracy.

The semantic data dictionary

A YAML file that teaches the system your company's vocabulary. Lives in data/dictionaries/. Someone must write it: draft with an LLM, then review by a human.

Analogy: a glossary handed to a new analyst. The analyst knows SQL but not that "churned" means canceled or past-due in the last 30 days, or that amounts are in cents. The dictionary is that glossary, and we hand over only the relevant lines for each question.

Beyond content: what the dictionary system itself needs

Format + validation

A strict schema for the YAML (Pydantic model) so a typo is caught at load time, not at answer time.

Executable metrics

Every metric snippet is run against the database in a test; a broken definition fails the build. A test also checks every referenced table and column still exists.

Always-on vs retrieved

Global rules (cents, pinned date) go in every prompt. Table and metric entries are retrieved per question to save tokens.

Examples, not only rules

Question-to-SQL exemplars are often more effective than prose rules for small models. They can live beside the dictionary and be retrieved the same way.

Prompt budget

On a 4 GB GPU we aim for roughly 1.5k to 2k prompt tokens total. The dictionary share must be a small slice.

Prove it helps

A dictionary can also hurt (too many or wrong entries confuse a small model). Eval with and without it, and measure dictionary-entry retrieval recall separately.

One dictionary per database, and how big it gets

Each database (a "profile" in data/profiles/) has its own file, e.g. data/dictionaries/saas.yaml. Shared across projects: the YAML format, the generator that drafts a skeleton from the database, the validators, and reusable metric templates. Not shared: what the business words mean.

Dictionary step 2: models and loader

The dictionary is a YAML file written by a person, so it will contain typos and copy-paste mistakes. This step builds the front door: it reads the file once, checks everything, and either hands back a trusted Python object or a clear error. After that, no other code needs to re-check it. The idea is called parse, don't validate.

Two YAML traps, tested on purpose

Duplicate keys

PyYAML keeps the last duplicate and silently drops the earlier one, so a copy-paste slip could erase a metric. Our loader raises: duplicate key 'metrics' on line 62 (first used on line 39).

The "Norway problem"

YAML 1.1 reads unquoted no, on, off, yes as booleans (a country code NO for Norway becomes false). Our own org_settings values are on/off. Strict string fields reject the boolean, and the error says to put the word in quotes.

Messages are part of the feature. The first version of the Norway error just said "Input should be a valid string", which makes the user guess. We saw it, judged it unhelpful, and added a targeted hint. Always read your own error messages as if you were the person who has to fix the file.

How the tests are written

  • Start from one valid fixture (tests/unit/fixtures/dictionary_valid.yaml).
  • Change exactly one thing per test, and assert the error names the exact field path.
  • A mutate() helper asserts the text to change really exists, so a test cannot pass by accidentally testing nothing.
  • 31 tests now pass in total; ruff is clean.
A test of ours was wrong, and the code was right. I expected a structural typo and a bad cross-reference to be reported together. Only the typo appeared: Pydantic runs "after" validators (our cross-reference rules) only when the fields themselves are valid. We kept the behaviour, rewrote the test to say so, and added a second test documenting it. When a test fails, decide whether the code or the expectation is wrong before touching either.

Working

Dictionary step 3: introspection and the draft

Introspection means asking the database to describe itself. Postgres keeps a catalog (pg_class, pg_attribute, pg_constraint) listing every table, column, key and CHECK rule. We read that catalog, never the rows, and use it to write a draft dictionary. Names then come from the database instead of from typing, so a typo like organisations cannot get in at the source.

Two ideas worth remembering

Structure is not data

Allowed values come from CHECK constraints (the schema), not from SELECT DISTINCT on rows. That respects the rule "never index row data or personal data", and the values are guaranteed complete because the database enforces them.

Heuristics need a human

The generator flags columns named like email, full_name or postal_code as pii: true # TODO confirm. It is a guess from names. A person confirms each flag in step 4 (for example ip_country is a coarse location, so is it personal?).

Gotcha: localhost hung on Windows. It resolves to IPv6 (::1) first, but Docker publishes the port on IPv4 only, so the connection waited instead of failing. Use 127.0.0.1, and always set a connect_timeout so a down database fails in seconds, not minutes.
Two places must agree, so a test guards them. The pinned date lives in the Docker loader script and in config.py. A unit test reads the script and fails if the defaults differ. When duplication cannot be avoided, test it.

How a metric becomes SQL

A metric is stored as a template, for example ... canceled_at > {today} - make_interval(days => {window_days}). core/metric_render.py fills it in: {today} becomes TIMESTAMPTZ '2026-11-05 12:00:00+00' and each parameter becomes an integer. Only declared parameters can be overridden and only integers are accepted, so nothing free-form is ever pasted into SQL (a test tries "1; DROP TABLE x").

A mistake the tests would have caught. My first sketch was {today} - {window_days}. In Postgres you cannot subtract an integer from a timestamp with time zone (it works for plain dates). That is exactly why every metric is executed in step 5 instead of just being read.

The red-team set, and two findings about our own safety

"100% of attacks blocked" is meaningless without a list of attacks. data/eval/redteam.yaml holds 26 of them (writes, DDL, privilege abuse, stacked statements, denial of service, personal-data requests, prompt injection). Tested now

19 attacks assigned to db_role run as the real read-only login, one connection each, always rolled back, with table row counts compared before and after. All are refused by the database.

Also tested now

The parser, limits and personal-data layers now exist (validation/guard.py, next section), and every attack that has SQL is run through them without a database.

Two findings (both verified by running them)

Good: two locks, not one

Even after a session turns read-only mode off, DELETE, UPDATE and CREATE TABLE still fail with InsufficientPrivilege, because the role was granted only SELECT. My first version of that test was wrong: the SET had not taken effect inside the open transaction, so the refusal came from read-only mode. Using autocommit made the lock really off.

Gap: the timeout is a default, not a wall

A session can run SET statement_timeout = 0 and remove the 10-second limit. So the Guard must reject SET statements and set the timeout itself on every connection it opens. Recorded as the attack dos_disable_timeout.

Defense in depth, concretely. The role setting alone looked sufficient until we tried to break it. Always attack your own safety layers before trusting them.
Advanced

The Guard, built: parse, restrict, limit, then run

Between the model and the database sits validation/guard.py. It reads the SQL as a tree with sqlglot and either returns safe SQL (with a LIMIT) or raises GuardViolation naming the rule. validation/executor.py then runs approved SQL in a read-only transaction with a timeout that our code sets.

Why a tree, not a text search

Looking for the word "DELETE" fails in both directions: it blocks a harmless column called deleted_at and misses tricks. A parse tree knows what each piece is. Proof from our own red-team set: WITH d AS (DELETE ...) SELECT ... and SELECT * INTO new_table ... both parse as a plain Select at the root, so checking only the root type is not enough. The guard walks every node.

Three things we learned while building it

Tests that pass first time are suspect

All guard tests passed on the first run, so we disabled each protection in turn: with PII checking off, SELECT email went through; with the forbidden-node check off, the hidden DELETE went through. The tests do bite.

Probe for false alarms

Trying legitimate queries found that generate_series(...) (used for per-day time series) was rejected as an "unknown table". Table-valued functions are now allowed but still vetted as functions.

A leak we had not listed

SELECT row_to_json(u) FROM users u returns the whole row, emails included, without naming a blocked column. It is now refused, with tests, and the same for to_jsonb(users) and nested stars.

Timeout closed

The executor runs SET LOCAL statement_timeout inside its own transaction (an integer we format, never model text). Tests: a 200 ms limit cancels pg_sleep(5); the connection still works afterwards; the setting does not leak to later queries.

Honest limit of "100% blocked". The red-team set and the guard were written by the same author, so passing it proves the guard handles known attacks, not that it is complete. The set must keep growing (and ideally be extended by someone else) as new tricks appear.

The second lock, in the database itself

The reviewer's best advice was not a Guard rule. Our read-only role could still SELECT every column, so any Guard miss was a real leak. We now generate the role's privileges from the dictionary: REVOKE ALL, then GRANT SELECT (only the non-PII columns). A table-level grant cannot be reduced by a column-level revoke, which is why it is revoke-then-grant. Now SELECT email FROM users and SELECT * FROM users fail with InsufficientPrivilege, even through table_to_xml, while count(*) and ordinary columns still work. The file data/schema/grants/copilot_ro.sql is generated (scripts/gen_column_grants.py) and a test fails if it is stale.

Blocklist vs allowlist

A blocklist names what you thought of; an allowlist names what you decided is safe. When the attacker's vocabulary is unbounded (database functions), only the allowlist is sound. Our legitimate queries used zero unrecognised functions, so the allowlist cost nothing.

Authors cannot review themselves

Our guard and red-team list shared an author, so "100% blocked" only meant "all attacks we thought of". A reviewer with a different mindset found 13 more. Each is now a permanent regression test.

Layers must be independent. If a layer's failure is only caught by the layer next to it written by the same person with the same blind spots, you have one layer. The database privilege lock does not share any code or assumption with the Guard.

The golden set: 50 verified questions, and how we scored them

A golden item is a business question plus a SQL answer whose result rows are the truth. Fifty were written (five domains, ten each: easy, medium and hard) and every one was checked by executing it through the Guard as the read-only role, twice, for identical rows. Nothing is "correct" because someone said so.

How the work was organised (orchestration)

  • Orchestrator (me) built the format, the loader, the helper scripts (show_schema, run_sql, check_golden) and one shared brief with the rules, definitions and pitfalls. Doing this once, in a file, kept each agent's prompt short and the instructions identical.
  • Five small, fast agents each wrote 10 items for one domain in parallel and had to iterate until check_golden reported 0 failures: a mechanical, self-checking job suited to a cheap model.
  • One strong reviewer read all 50 items against the business definitions, and attacked the Guard (previous section). Reviewing is where the expensive model pays off.
  • A small agent applied the fixes from a precise per-item list, then the checker re-verified.

The scoring rule (execution accuracy)

Rows are compared, not SQL text. Columns match in any order but their count must agree; row order is ignored unless the question is a ranking; numbers match within 0.05; booleans never equal numbers (in Python True == 1, a bug our own test caught); dates compare as text. Percent and fraction are different answers on purpose.

Seed artifacts the writers noticed: all 133 lost sales deals share one close date, and two marketing channels show 100% lead conversion. These make some questions weak tests and are on the list to fix in the seed.

Verify and repair: trust, but let the database check

Idea: a small model often invents a column. Ask the database to plan the query (EXPLAIN, never EXPLAIN ANALYZE, which would run it). Planning is milliseconds and finds bad columns, bad types and bad syntax. If it fails, send the model the error plus real facts (the true column list of the tables it used, and which table a missing column actually lives in) and let it retry, at most twice.

Analogy: a spell-checker that also hands you the dictionary page. Files: validation/verify.py (Guard, then EXPLAIN, then hints), graph/repair.py (the bounded loop, tested with fake model and DB), build_repair_message in the one prompt builder.

What we measured (dev split, 33 questions): queries that run rose 76% to 91%, but correct answers only 51.5% to 54.5% (one question). Most remaining mistakes are valid but wrong SQL (wrong filter, wrong definition), which no error message can reveal. Retries also pushed p95 latency from 4.2 s to 12.4 s, over the 10 s budget. So repair is a safety net that hides crashes, not an accuracy lever; fine-tuning is the lever.
Gotchas: (1) database errors for alias.column have no quotes, so our first hint pattern missed exactly the hard cases; (2) hints must never list personal columns; (3) the dev/test split (validation/splits.py, fixed hash of the template name) exists so we tune on dev and spend test only once.

Fine-tuning a small model with QLoRA

A base model (Qwen2.5-Coder) already knows SQL. Fine-tuning teaches our JSON format, strict Postgres style, how to patch from an error, and when to answer MISSING_SCHEMA_KEY.

LoRA

Freeze the base. Train two small matrices per layer whose product is the update. Far fewer trainable numbers, same quality in practice.

QLoRA

Same, but the frozen base is kept in 4-bit so a 1.5B-3B model trains on a free 15 GB Colab T4. Libraries: trl, peft, bitsandbytes.

SFT

Supervised fine-tuning: show (prompt → ideal answer) pairs; the loss is computed on the answer tokens.

What one training example holds

PROMPT   = question + exactly the context seen at run time
           (pruned DDL, dictionary rules, FK hints, dialect hints)
RESPONSE = {"sql": "...", "tables_used": [...], "assumptions": [...]}

Data rules that matter most. (1) Execute every golden query on the seeded DB and drop failures. (2) Split train/test by query template, not randomly, or you test on memorized shapes. One model, many databases: what is fine-tuning actually for?

The schema and dictionary arrive in the prompt on every question. Fine-tuning is meant to teach skills that do not depend on any one database: reading the context it is given, our JSON format, strict Postgres style, fixing a query from an error, and refusing when a column does not exist. It is not meant to memorize our tables.

The catch. If every training example comes from one schema, the model can quietly learn our tables instead of the skill. It then scores well on our eval and fails on a new schema. This is the central risk of the whole multi-database idea.
StrategyTrained onCost of a new databaseRisk
A. Schema-specificOnly our schemaRetrain per databaseGreat here, poor transfer
B. Schema-agnostic skillsMany schemas, names shuffledDictionary + index onlyNeeds varied data (more work up front)
C. No fine-tuneNothingDictionary + index onlyLower accuracy; also our baseline
Plan. Build for our database first (that is how the pipeline is learned), but write the training-data generator against any introspected schema, not against ours. Most SQL patterns are structural (join along a foreign key, group by an enum, filter by a date range); only metric definitions are business-specific and those come from the dictionary. Later add two or three small synthetic schemas (library, hospital, e-commerce) and hold one entirely out of training as a transfer test.
Anti-memorization

Vary which tables appear in each prompt, shuffle their order, and rename tables and columns in some examples, so the model must read the prompt instead of recalling.

New Postgres database

Profile YAML, read-only role, draft dictionary from the generator, human review of metrics, build index, auto-generate a test set plus a few real questions, run the eval, retrain only if the score is too low.

New dialect

Bigger step than a new database: dialect-specific training data, validator and safety rules (see the Dialect plug-in).

Decision (2026-11-05): A now, B later. We train on our one schema first. Keep the generator schema-agnostic so moving to B is cheap, and treat high scores on our own eval with caution until a held-out schema exists.

Effort for a new database is not measured; the human-heavy steps are the metric review and the real test questions.

LangGraph: a state machine with retries

LangGraph runs nodes (Python functions) connected by edges, all reading and writing one shared state. Its strength here is the cycle: fail → patch → retry.

from langgraph.graph import StateGraph, END

g = StateGraph(State)
g.add_node("generate_sql", generate_sql)
g.add_node("validate_sql", validate_sql)
g.add_node("patch_query", patch_query)
g.add_edge("generate_sql", "validate_sql")
g.add_conditional_edges("validate_sql", route,   # returns "ok" | "retry" | "stop"
    {"ok": END, "retry": "patch_query", "stop": END})
g.add_edge("patch_query", "validate_sql")
Limit of EXPLAIN. It proves the SQL plans, not that the answer is right. A wrong-but-valid query passes. That is why evaluation compares result rows. Never use EXPLAIN ANALYZE: it executes the query.

Model serving: vLLM vs llama.cpp (and what changes for us)

A trained model is just files. To answer questions it must be loaded into memory and wrapped in a program that accepts text and returns text. That program is an inference server.

Analogy: a coffee machine. Training is designing the recipe. The inference server is the machine on the counter that takes an order and makes a cup. vLLM is a big café machine built to serve a queue of customers at once on a powerful GPU. llama.cpp is a compact machine for a home kitchen: one person, modest hardware, still good coffee.
vLLM

The high-throughput server

Python server for GPUs. Its trick, continuous batching plus paged KV-cache, serves many users at once and can hot-swap several LoRA adapters on one base model. Built for Linux and big VRAM. Not native on Windows; needs WSL2/Docker GPU passthrough and more than 4 GB VRAM.

llama.cpp

The runs-anywhere server

C/C++ engine that runs quantized models on CPU, GPU or both. llama-server exposes an OpenAI-compatible HTTP API. Native Windows binaries exist. Ideal for one user on a 4 GB GPU.

GGUF

llama.cpp's file format

One file holding weights (already quantized, e.g. Q4_K_M = about 4.5 bits/weight) plus tokenizer metadata. A 1.5B model becomes roughly 1 GB.

Why the Colab adapter cannot go straight to your PC

  • Different formats. bitsandbytes 4-bit weights and PEFT files are not GGUF. llama.cpp cannot read them; something must convert.
  • The adapter alone is not a model. It is only a delta. Either merge it into the base (then convert and quantize), or convert the adapter to a GGUF LoRA and load it over a GGUF base with --lora. Both routes need a conversion.
  • Merge into the 16-bit base. QLoRA trained against a 4-bit-rounded copy of the base, but the merge uses the original 16-bit weights, so there is already a small mismatch.
  • Quantization is the step most likely to hurt. Q4_K_M rounds the merged weights a second time. The loss is usually small, but only the eval can tell. If it drops, try Q5_K_M or Q8_0 (bigger file, closer to full precision; check it still fits in 4 GB).

The three-step recipe: SFT, then GRPO, then voting

The best small-model Text-to-SQL papers (SLM-SQL, FINER-SQL, Arctic-Text2SQL-R1) share one pattern. Method moves accuracy more than model size. This is our roadmap after the basic fine-tune works.

Stage 1 · SFT

Imitation

Loss is computed on the answer tokens only. Limited by how good and varied the examples are. Our template-made data is correct but narrow.

Stage 2 · GRPO

Trial and reward

No gold SQL needed per sample, only a gold result. The model tries, the database grades. Reward is simple: 1 if rows match, else 0 (plus small bonuses for valid JSON). It rewards different-but-correct SQL that SFT would punish.

Stage 3 · Voting

Self-consistency by execution

Group candidates by their result set, not SQL text, and pick the biggest group. Wrong answers tend to disagree with each other; right answers agree.

Success criteria: how we know we are done

Without numbers, "it works" is an opinion. These are the v1 targets, agreed up front so we cannot move the goalposts after seeing results.

Accuracy

≥ 70% execution accuracy

On held-out query templates, scored by comparing result rows. This number is a guess; we revise it once the first baseline exists.

Safety

100% of attacks blocked

Every write, injection and PII request in the red-team set must be stopped by the guard.

Speed

p95 latency < 10 s

95% of questions answered within 10 seconds on the laptop, including retries.

Data quality

Golden queries verified

Every golden query is executed against the database and its result checked before it enters the eval.

Why held-out templates? If test questions share a template with training questions, the model can pass by memorizing shapes. Testing on unseen templates measures real generalization, which is what the 70% target refers to.
Concept: p95. The latency that 95% of requests beat. It shows the slow tail that an average hides.

Self-quiz

Answer in your head or on paper first, then click to reveal.

1. Why do we retrieve schema instead of pasting all of it?

Small models drown in noise, hallucinate columns, and use long contexts poorly (start/end better than middle). Retrieval keeps only the few relevant tables plus rules.

2. Why use both embeddings and BM25?

Embeddings catch meaning ("client" ≈ "organization"); BM25 catches exact identifiers like mrr_cents. RRF merges the two rankings.

3. What does RRF compute?

For each item, the sum over rankings of 1/(k + rank). Items ranked high in several lists get the highest score.

4. What is the difference between LoRA and QLoRA?

LoRA trains small adapter matrices on a frozen base. QLoRA also stores the frozen base in 4-bit so training fits on a small GPU.

5. Why does EXPLAIN not prove the answer is right?

It only checks the query is valid and plannable. A wrong-but-valid query passes, so evaluation compares result rows to golden results.

6. Why split train/test by query template?

A random split leaks near-identical questions into test, inflating scores. Template split tests real generalization.

7. Name the four safety layers.

Read-only DB role; parse with sqlglot (single SELECT, blocked functions); timeout + forced LIMIT; hide sensitive columns.

8. Why are init scripts in Docker not re-running?

They only run on an empty data volume. Use down -v to wipe it, then up -d.

9. Why must training and production share one prompt builder?

A format mismatch between training and inference silently weakens the fine-tuned model.

10. How would you add MySQL later?

Implement dialects/mysql/, generate data and train a mysql-v1 adapter, register it with the model server, add a dictionary and profile. No change to graph/API/UI.

11. Is DECIMAL inaccurate? Why store money as integer cents then?

No: Postgres NUMERIC/DECIMAL is exact. Binary FLOAT is the inexact one. Integer cents is a convention that is exact and portable, but the model must divide by 100.0, so the dictionary documents it.

23. If the model is fine-tuned on one schema, what is the main risk when we add a second database?

It may have learned our specific tables instead of the general skill of reading the schema and dictionary in the prompt. The fix is schema-agnostic training data (several schemas, shuffled and renamed) and a held-out schema to measure transfer.

24. Why install the project with pip install -e instead of a normal install?

An editable install links the venv to your source folder, so edits take effect immediately and imports always see the current code, while still testing that the package is properly installable.

25. Why do integration tests skip instead of fail when Docker is off?

They are marked integration and the fixture skips when the database is unreachable, so the fast test run never breaks because of the environment, while a real failure with the DB up still shows.

26. What does "parse, don't validate" mean for the dictionary?

Check the file once at load time and return a trusted, frozen object. Every other part of the system then uses it without re-checking, and a bad file fails immediately with a clear message instead of misbehaving later.

27. Why does the loader reject unknown fields and duplicate keys instead of tolerating them?

Both mistakes are silent by default: a typo'd field is ignored and a duplicate key quietly overwrites the earlier one. Either would degrade answers with no error, so we make them loud.

28. What is the "Norway problem" and how do we defend against it?

YAML 1.1 turns unquoted no/on/off/yes into booleans. Strict string fields reject the boolean, and the error tells the author to quote the value.

29. A dictionary says organisations but the table is organizations. Which step catches it?

Not the loader (step 2): the name is a valid identifier and the loader never sees the database. The step 5 tests do ("every dictionary table exists" and "every database table is covered"). Step 3's draft generator prevents it by copying names from the catalog.

30. Why read allowed values from CHECK constraints instead of SELECT DISTINCT?

CHECK constraints are structure, so no row data is touched, and they are complete by definition because the database enforces them. DISTINCT would read data, could miss rare values, and could leak personal data.

31. Why define a Dialect Protocol instead of calling Postgres code directly?

The pipeline then depends on a contract, not a database. A new database means one new adapter plus a profile and dictionary, with no change to retrieval, graph, API or UI.

32. Why is {today} - {window_days} a bug in Postgres, and how did we catch this class of mistake?

A timestamp with time zone minus a plain integer is not valid (it only works for dates). The fix is make_interval(days => N). We catch such mistakes by actually executing every metric against the database in tests instead of only reading them.

33. The login data made "active users" nearly equal to "all users". Why is that a problem for evaluation, and what did we do?

A metric that returns almost everyone cannot be told apart from a plain count, so a wrong query could still score as correct. We made activity uneven (engaged, lapsing, dormant, never) and added a check that fails if it turns uniform again.

34. The role has a 10-second statement timeout. Why is that not enough on its own?

A session can run SET statement_timeout = 0. The Guard must reject SET statements and apply the timeout itself on every connection.

35. How did we make sure a test of the "read-only" lock really tested the lock?

The first version raised an error for the wrong reason (the SET had not taken effect inside the open transaction). Running with autocommit switched read-only mode truly off, and the writes were then refused by privileges. Always check that a passing test would fail if the protection were removed.

36. Why does the guard inspect the whole parse tree instead of just checking the statement type?

A DELETE inside a WITH clause, or SELECT ... INTO, parses as a Select at the root but still writes. Walking every node finds it. A text search for keywords is both too strict (a column named deleted_at) and too weak.

37. SELECT row_to_json(u) FROM users u never mentions a blocked column. Why is it still a leak?

The whole row is returned as JSON, including email and full_name. The guard treats a bare table alias used as a value as a whole-row reference and refuses it when the table holds personal data.

38. Our guard passed every red-team attack. Does that prove it is safe?

No. It proves it handles the known attacks, and the same author wrote both. Safety comes from layers (parser, privileges, read-only transaction, timeout) plus a red-team set that keeps growing.

39. Why is an allowlist of SQL functions safer than a blocklist?

The database has hundreds of functions that read tables or execute SQL passed as text, and an attacker only needs one we forgot. An allowlist refuses everything we have not judged safe, so unknown functions fail closed.

40. Why generate column-level grants (revoke everything, then grant the safe columns) instead of just revoking the PII columns?

A table-level SELECT covers every column and a column-level REVOKE cannot subtract from it. Revoking all and granting only the non-PII columns is the only way to leave some columns unreadable.

41. A golden question returns an extra id column next to the name. What goes wrong when a model answers correctly?

Rows are compared by column position and count, so a correct two-column answer does not match the three-column golden answer and is scored wrong. Golden SQL must return exactly the columns the question asks for.

42. A "top 5" golden question has a tie for 5th place. Why is that a problem?

Which tied item makes the cut is arbitrary, so equally correct answers can differ. Change N, use a threshold, or compare as a set so the boundary is not ambiguous.

43. Why use a strong model for review and cheap models for writing the first draft?

Drafting is mechanical and can be checked by a script (does it execute, is it deterministic). Judging whether a question and its SQL truly mean the same thing, or finding a bypass, needs deeper reasoning, and is done once, so the cost is small.

44. Our baseline gave 52% with all tables and 54% with perfect table selection. What does that tell us?

For this model, picking the right tables is not the bottleneck; writing correct SQL is. So fine-tuning and the verify-and-repair loop are the bigger levers, and a perfect retriever alone would add little. (With 50 questions, 2 points is a single question: noise.)

45. Why does pii: "yes" (in quotes) fail with StrictBool but pass with plain bool?

Plain bool in Pydantic's default mode converts strings like "yes", "true", "1" to True. StrictBool accepts only real booleans. We want the strict one: a quoted word in a safety flag is almost certainly a mistake, and it should fail loudly rather than silently become True or False.

20. Why do the golden answers need a pinned "today"?

Questions like "churned this month" depend on the current date. If the data hangs off NOW(), the right answer changes every day and the eval expires. Pinning the date (2026-11-05, also injected into the prompt) keeps answers stable.

21. All 35 data checks passed on the first run. Why did we still corrupt the data on purpose?

A check that can never fail proves nothing. Injecting known violations in a rolled-back transaction showed each check actually detects its rule.

22. What is a distractor table, and why add them?

A plausibly named table that is wrong for a question (plans vs subscriptions, employees vs users). With only 8 tables retrieval is trivial; distractors make table-pruning quality measurable.

12. Why is "total revenue" ambiguous in our schema?

payments links to either an order or an invoice (two nullable FKs), and can be refunded or failed. The dictionary must define which rows count (e.g. status = 'succeeded', both sources).

13. Why do we use llama.cpp instead of vLLM on this PC?

Your GPU has 4 GB VRAM and runs Windows. vLLM is Linux-oriented and wants more VRAM and throughput than one user needs. llama.cpp runs quantized GGUF models natively on Windows within 4 GB.

14. What extra steps does the llama.cpp path add after training, and why evaluate after them?

Merge the adapter into the base, convert to GGUF, quantize (e.g. Q4_K_M). Quantization can reduce accuracy, so the eval must run on the exact quantized file we serve.

15. Why does switching serving engines not require rewriting our code?

Both expose an OpenAI-style HTTP API and our generation client only needs a base URL and model name, so the engine is a replaceable detail.

16. Which step between Colab and your PC is most likely to cost accuracy, and what do you do about it?

Quantization to Q4_K_M (plus the small mismatch from merging into the 16-bit base rather than the 4-bit one QLoRA trained against). Evaluate the exact file you serve; if it drops, try Q5_K_M or Q8_0 if it still fits in VRAM.

17. Why is Qwen3-4B-Instruct-2507 a challenger but not an automatic choice?

It is more capable but nearly fills 4 GB VRAM and trains slower on a T4. (Plain Qwen3-4B also has thinking mode on by default, which is why we use the 2507 Instruct variant.) A bake-off against the 1.5B on our own eval decides.

18. Why is Qwen3.5-4B parked for now?

Its hybrid DeltaNet layers use custom kernels that are slow on a T4, Unsloth advises against 4-bit QLoRA for it, and its documented 4B LoRA recipe needs about 10 GB and bf16, which a T4 lacks.

19. What techniques lift small-model SQL accuracy more than swapping base models?

Supervised fine-tuning followed by reinforcement learning with an execution reward (GRPO), and sampling several candidates, executing them and voting at inference.
